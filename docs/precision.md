# Анализ точности замеров (30.09.2026, measure_schema 7)

Проверено на живом Р7 2026.3.2, фикстура 50К (лист «1»: 50 001 строка × 49
столбцов), 16 ядер. Метод: для каждой операции независимо от инструмента
сняты длительность вызова api, время ответа редактора после него и загрузка
каждого процесса Р7 каждые 50 мс; результат сравнён с цифрой инструмента.

## Что искажало цифры и что сделано

### 1. Конец операции: опрос CPU → ответ редактора

После вызова api редактор свободен через 0–4 мс, после копирования — через
15–120 мс (дописывается буфер обмена). Позже идут только редкие многопоточные
всплески CPU (фоновая сборка мусора), интерфейс они не блокируют. Детектор по
CPU время от времени принимал такой всплеск за продолжение операции и
прибавлял 0.2–1 с: Ctrl+A давал 0.84 / 1.88 / 0.84 с при вызове 0.84 с.

Теперь на CDP-пути конец операции определяет `_wait_renderer_idle`: пинг
(`R7WebDriverConnector.ping`, пустой `Runtime.evaluate`) отвечает, когда
главный поток редактора свободен. Медленный ответ (> `OP_PING_FAST_SEC`,
10 мс) значит «был занят до момента ответа». Конец — момент последнего
медленного ответа в окне `OP_PING_QUIET_SEC` (0.3 с) либо возврат вызова.
Статус всегда `ok`, разрешение ~1 мс. Опрос CPU остался для клавиатурного
пути и экспорта.

Слепая пауза между шагами цепочки (копирование → вставка) заменена на
`_cdp_settle` — тот же пинг до быстрого ответа. Пауза вычиталась по
процессорному времени с шагом 15.6 мс (шум ±16 мс на операции в 230 мс).

Автосохранение должно быть отключено (`_suspend_autosave`): иначе после
каждой правки редактор ещё 2.7 с пишет файл восстановления.

### 2. Состояние перед тестом задано явно

У каждого теста — подготовка вне замера (`_with_prepare`), результат не
зависит от соседних тестов и от того, какие из них отмечены.

| Тест | Подготовка | Что было |
|---|---|---|
| Выделение всех ячеек | рабочий лист, A1 | лист, оставшийся от прошлого теста |
| Копирование всех ячеек | рабочий лист, выделен весь | — |
| Вставка большого массива | копия листа в буфере, новый пустой лист | создание листа (0.7 с) в замере; буфер — что осталось |
| Добавление нового листа | рабочий лист, A1 | 0.04 с с копии листа, 1.05 с с исходного |
| Добавление столбца ×2 | рабочий лист, B1 | «лист левее активного»: два теста шли на разных листах, 1.6 и 3.3 с |

Буфер обмена проверяется по `GetClipboardSequenceNumber` (`_clipboard_seq`),
запомненному после копирования листа: не совпал — лист копируется заново вне
замера.

### 3. «Вставка большого массива»: новый лист на каждый повтор

После отката вставки лист пуст, но вставка в него идёт 22.2 с против 20.3 с
на новом листе. Очистка redo (`History.Clear_Redo`) и сборка мусора не
помогают. `_paste_big_prepare` убирает лист прошлого повтора откатом его
создания и создаёт новый: 20.1 / 20.7 / 20.5 / 20.7 с. Ручной замер
пользователя секундомером — 20 с.

`api_ms` для вставки (2–3 с) занижен: основная работа идёт после возврата из
функции. Верное значение — `time`.

### 4. Экспорт: от нажатия «Сохранить» до записи файла

Раньше в замер входили открытие диалога, выбор типа и посимвольный ввод
пути — 2–3 с работы инструмента с разбросом (PDF 88.3 с при конвертации
85.4 с). Теперь `_uia_select_saveas_type` ставит `_export_go_at` перед
кликом «Сохранить», и `_save_as_format` относит всё до него к подготовке.
Вычитается только время, пока окна Р7 (предупреждение о формате, параметры
CSV) ждали ответа. Конец — всегда запись файла (`_op_completed_at`);
активность Р7 после неё в экспорт не входит. PDF: 85.1 с при конвертации
84.9 с, разброс 0.2 с.

### 5. Открытие файла

* Модалку тяжёлого пересчёта на CDP-пути закрывает пробник, вставший в
  очередь редактора ещё во время загрузки, — в момент появления, ожидание
  ≈ 0. Если её закрывает обычный опрос, время ожидания считает сама страница
  (`waited_ms`: `MutationObserver` на `body`).
* Повторы открытия — независимые холодные старты, первый не отбрасывается
  (`discard_warmup=False`). По умолчанию 5 повторов.
* **Разброс 9 → 12–14 с вызван диском, а не Р7.** При открытии x2t пишет
  ~330 МБ в `%LOCALAPPDATA%\R7-Office\Editors\data\recover`. На стенде это
  диск C: (Crucial BX500, SATA): сброс 328 МБ занимает 0.8–4.7 с; диск E:
  (Samsung 990 PRO) — 0.13 с. x2t работает 4 с либо 5–9 с при одинаковом
  процессорном времени 2.9 с. Переменная TEMP на расположение этой папки не
  влияет. Инструмент считает ожидание x2t (`x2t_wait_sec` = время работы −
  процессорное время) и при разбросе ≥ 1 с ставит пометку `disk_note`
  («диск» в отчёте).

* **Свободное место.** На диске C: стенда оставалось 1.4 ГБ из 111; третий
  экспорт в XLTX упал в конвертере с кодом `0x50`. `_capture_environment`
  теперь пишет свободное место на дисках с папкой данных Р7 и `%TEMP%`
  (`disk_free_gb`) и предупреждает, если меньше `ENV_MIN_FREE_DISK_GB` (5 ГБ).

### 6. Окна Р7 — только окна процессов Р7

Заголовка мало: «Р7-Офис» есть и во вкладке браузера «Техническая поддержка
Р7-Офис - Google Chrome». Из-за этого:

* поиск окна-предупреждения при экспорте нашёл вкладку Chrome, настоящее
  предупреждение осталось без ответа — CSV и XLTX сорвались;
* тест своего файла принял вкладку за окно Р7 («холодный старт 0.00 с») и
  закрыл Chrome через `WM_CLOSE`.

`_is_r7_window` проверяет имя процесса-владельца, `_find_r7_window` — общий
поиск для трёх воркеров. `_close_r7_gracefully` и `_ensure_foreground_click`
отказываются работать с чужим окном; `_find_window_hwnd` принимает
`owner_pids`.

### 7. Тест своего файла

ВПР там вводился клавишами и тянулся Ctrl+D — Р7 2026.3.2 этого не
принимает, секундомер мерил пустоту. Теперь это тот же замер, что у теста
«Функция ВПР» (`_vlookup_prepare` / `_vlookup_op` через
`_measure_op_repeated`): 20 000 строк — 1.25 с.

### 8. Статистика

Прогрев отбрасывается, только если после него остаётся ≥ 3 прогонов
(`MIN_RUNS_FOR_STATS = 4`): медиана двух — их среднее.
