# Документы (.docx): операции, готовность, откат

Этап 5, пункт 1 плана «до 20», часть «документы» (07.10.2026). Презентации —
`docs/presentation-ops.md`.

## Что меряется

Набор `suites/docs.toml` (`[suite] editor = "document"`), запуск:

```bash
.venv/Scripts/python.exe -m r7 run --suite suites/docs.toml --gate
```

| Тест | Что делает в замере | Подтверждение |
|---|---|---|
| Повторное открытие файла | холодный запуск Р7 с документом, как у таблиц | готовность + вёрстка (ниже) |
| Вставка 100 страниц (разрывы) | 100 × `asc_AddBlankPage` одним вызовом JS, курсор в начале документа | история сдвинулась и страниц стало больше хотя бы на 50 |
| Смена стиля всего документа | выделить всё, `put_Style("heading 2")` | история сдвинулась |
| Поиск и замена по документу | `asc_replaceText` всех «квартал» → «период» | история сдвинулась |
| Сохранение в PDF (документ, x2t) | общий «Сохранить как», тип `(*.pdf)` | файл — `%PDF-` |
| Сохранение в DOCX (документ, x2t) | то же, тип `(*.docx)` | в `[Content_Types].xml` — `wordprocessingml.document.main` |

Имена — `r7_doc_ops.DOCUMENT_TEST_DEFINITIONS`, повторы по умолчанию —
`DEFAULT_DOC_RUNS` (правки 5, экспорт 3). «Пересчёт полей» не сделан:
в фикстуре нет полей, а дешёвого api-вызова без подготовки документа нет.

## Фикстура

`r7/doc_fixtures.py`, только стандартная библиотека. `generate_docx(path,
pages=100, seed=42)` пишет ~100 страниц A4: главы `heading 1` с разрывом
страницы перед каждой, по три раздела `heading 2`, абзацы обычного стиля
по 70–100 слов (около шести на страницу), одна таблица 30 × 5 в середине.
В каждом абзаце есть слово `REPLACE_WORD` («квартал»). Один seed — побайтно
один файл (фиксированные даты в zip). Каноническое имя —
`TestFiles/r7-test-doc-100p.docx`; нет файла — воркер создаёт его сам.

## Как устроен прогон

Воркер не копируется. `_document_worker` ставит `_run_editor = "document"`
и зовёт `_spreadsheet_worker`. Примесь `DocumentRunMixin` (`r7/doc_run.py`)
стоит в `R7Testovarka` первой и в режиме документа перехватывает методы,
где редакторы расходятся; для таблиц отдаёт `super()`:

| Метод | Документ |
|---|---|
| `_locate_test_file` | фикстура документа, нет — генерация |
| `_make_run_ops` | `r7_doc_ops.DocumentOps` вместо `SpreadsheetOps` |
| `_wait_until_r7_ready` | общий детектор + досчитанная вёрстка |
| `_wait_renderer_idle` | пинг + досчитанная вёрстка |
| `_history_snapshot`, `_restore_history` | история документа, `Undo` до снимка |
| `_flush_pending_cdp_verify` | перечитывает состояние документа |
| `_cdp_log_api_info`, `_suspend_autosave`, `_restore_autosave` | через пролог документа |
| `_build_full_report` | `"editor": "document"` (у таблиц — `"spreadsheet"`) |

Всё, кроме `_locate_test_file` и `_make_run_ops`, — общая часть
нетабличных редакторов: JS берётся из профиля (`EditorProfile`,
`_editor_profile()`, у документа — `DOCUMENT_PROFILE`), поэтому те же методы
работают и для презентаций со своим профилем (`r7/pptx_run.py`).

JS — `r7/doc_js.py`. Свой пролог (`DOC_API_PRELUDE`): api — это `editor`
(или `Asc.editor`, или `DE.getController('Main').api`) с `getCountPages` и
`WordControl.m_oLogicDocument` без массива `Slides` (с ним — редактор
презентаций). Табличный `_API_PRELUDE` не тронут.
Операции собираются тем же `_op_js`: поля `ok`, `mutated`, `api_ms`,
`before`/`after`. `mutated = true` ставится прямо перед первым изменяющим
вызовом, и он последний (правило 7). Выделение всего документа перед
`put_Style` документ не меняет.

Снимок документа (`docState`): `pages` (`getCountPages`), `blocks`
(`Content.length` — абзацы и таблицы верхнего уровня), `historyIndex`,
`historyPoints`, `canUndo`, `recalcBusy`.

## Готовность и конец операции

Кнопка «Жирный» (`id-toolbar-btn-bold`) есть и в редакторе документов,
поэтому общий детектор (`ReadinessWait`) работает без изменений. Но большой
документ верстается порциями по таймеру уже после того, как кнопка
включилась. Поэтому после общего признака `_doc_layout_settle` опрашивает
состояние раз в `DOC_LAYOUT_POLL_SEC` (0,15 с):

- `FullRecalc.Id` есть и не `null` — вёрстка идёт, ждём;
- `recalcBusy === false` — готово с первого такого чтения;
- поле не читается (`null`) — готово, когда число страниц не меняется
  `DOC_LAYOUT_STABLE_POLLS` (2) чтения подряд.

Если итоговое состояние было уже на первом чтении, момент готовности
остаётся от общего детектора. Иначе он сдвигается на первое чтение
итогового состояния, маркер — `bold+layout` (`+layout_timeout`, если за
`DOC_READY_LAYOUT_TIMEOUT_SEC` = 60 с не досчиталось; тогда открытие —
верхняя оценка). Погрешность сдвига — шаг опроса плюс round-trip.

Конец правки на CDP-пути — та же логика поверх пинга: в паузах между
порциями вёрстки пинг отвечает быстро, и одна тишина пинга закончила бы
замер до конца вёрстки. Если после тишины вёрстка ещё шла, конец — момент
её досчёта, затем ещё одна тишина пинга (хвост после последней порции).

## Откат и подтверждение

Перед каждым повтором (`_doc_prepare`, вне замера): вёрстка досчитана,
курсор в начале документа (`MoveCursorToStartPos`), выделение снято. После
повтора — `Undo` до `History.Index` снимка (не больше
`DOC_UNDO_MAX_STEPS` = 400 шагов: «Вставка 100 страниц» — около сотни
точек), затем снова досчитанная вёрстка и простой Р7.

Проверка результата: история правок сдвинулась. У «Вставки 100 страниц»
ещё и число страниц — сразу после вызова оно не досчитано, поэтому проверка
откладывается и повторяется после конца замера (`_flush_pending_cdp_verify`
читает уже состояние документа). Не подтвердилось — повтор `unverified`,
в медиану не входит.

## Без CDP

Клавиатурного запасного пути у правок документа нет: «Вставка 100 страниц»
клавишами — сто нажатий в замере, «Поиск и замена» — слепая работа с
диалогом (правило 8). Нет CDP или api не выполнил операцию, не тронув
документ, — тест падает с ошибкой «нет CDP или api документа не выполнил
операцию». Экспорт идёт общим `_save_as_format` со своими запасными путями
открытия диалога.

## Отчёт

`performance_full_*.json` получает ключ `editor` (новый и необязательный,
схема не поднималась — правило 11; отчёт без ключа — таблицы). В HTML-отчёте
документа в блоке «Стенд» строка «Редактор: документы (.docx)». Тренды
держат операции документов отдельными линиями (`… · документы (.docx)`).
CLI отказывается сравнивать набор документа с табличным эталоном и
наоборот (код 3).

## Метрики интерфейса, трасса и Batch

Метрики интерфейса (схема 10: `ux_first_frame_ms`, `ux_longest_task_ms`,
`js_heap_mb`, `js_heap_delta_mb`) снимаются так же, как у таблиц. Операции
документа собираются `_op_js` с прологом `DOC_API_PRELUDE` и ставят
`__uxMark` сразу после `api_ms`. Взвод и сбор идут тем же прологом:
`EditorProfile.api_prelude` → `_ux_prelude` → `ux_arm`/`ux_collect(prelude=…)`.
С табличным прологом взвод уходил в верхнее окно, а метка — во фрейм
редактора, и поля оставались пустыми.

Трасса регрессий: `python -m r7 run --suite suites/docs.toml --baseline …
--trace-regressions` и `python -m r7 trace --op "Смена стиля всего
документа"` (редактор находится по имени операции, `--editor document` —
явно). Сессия трассы идёт в режиме документа (`editor_mode`): фикстура,
готовность с досчитанной вёрсткой, операции `DocumentOps`, откат истории.

Batch: в диалоге — переключатель «Документ (.docx)». Тестовый файл —
фикстура документа (нет — создаётся при запуске), на каждой версии
меряются все тесты `DocumentOps`: экспорт по 3 повтора, правки по
`BATCH_TEST_RUNS`. A-B-A работает так же. Сводка Batch пишет редактор в
заголовке и не показывает колонку ВПР.

## Живая проверка

Координатор 07.10.2026 проверил на Р7 2026.3.2 api `editor` во фрейме
глубины 1, `getCountPages`, `Content.length`, `History.Index` и наличие
`asc_AddBlankPage`, `put_Style`, `asc_replaceText`, `Undo`.

08.10.2026 весь набор `suites/docs.toml` прошёл на том же Р7: «Релиз
готов», 6 из 6 операций, ни одного `unverified` и `timeout`, 2,2 мин.
Что это подтвердило:

1. 100 вызовов `asc_AddBlankPage` дают ровно +100 страниц (101 → 201).
   Сразу после вызова `getCountPages` ещё показывает 101, поэтому
   проверка каждый раз откладывается до конца замера и там проходит.
   Время операции почти равно `api_ms` (0,96 с против 0,96 с), а самая
   длинная блокировка — 961 мс: вёрстка новых страниц идёт внутри вызова,
   замер её не теряет.
2. `put_Style` и `asc_replaceText` срабатывают и пишут одну точку истории.
3. «Сохранить как» открывается через вкладку «Файл», типы `(*.pdf)` и
   `(*.docx)` выбираются, x2t отдаёт файл с кодом 0.
4. Откат 100 точек `Undo` одним вызовом JS занимает около 0,5 с вне
   замера, следующий повтор начинается со 101 страницы.

`FullRecalc.Id` на этой сборке читается. Проба 08.10.2026 опрашивала
состояние каждые 5 мс на 10 повторах «Смены стиля»: `put_Style`
возвращается за 70 мс, вёрстка идёт ещё 0,6 с (страниц 101 → 146), флаг
держится до конца и ни разу не сбрасывается между порциями.

### Конец операции и шаг опроса вёрстки

Конец операции — момент первого чтения итогового состояния. До 08.10.2026
опрос шёл шагом 0,15 с, и шаг попадал в замер: «Смена стиля» выходила
0,77 с при настоящих ~0,71 с. Теперь шаг 0,05 с, как у пинга
(`DOC_LAYOUT_POLL_SEC`), а итог подтверждается вторым чтением
(`DOC_LAYOUT_STABLE_POLLS`) и при `recalcBusy` False тоже. Цифры документов
и презентаций до этой правки в среднем на ~0,05 с выше; схему отчёта не
поднимали, потому что таблицы правка не задела.

Порядок тоже другой: сначала досчёт вёрстки сразу после вызова api, потом
пинг. Вёрстка идёт порциями короче 10 мс, пинг их не видит. Раньше опрос
вёрстки шёл после тишины пинга (0,3 с), к первому чтению всё было готово,
и хвост «Вставки 100 страниц» (~0,15 с после возврата api) в замер не
попадал: время равнялось `api_ms`.

В одном прогоне «Смена стиля» дала 0,47 с: конец нашёлся по пингу, без
досчёта вёрстки. Причину живьём поймать не удалось. Теперь такой случай
пишет в журнал «Состояние документа не прочитать — конец операции по
пингу», и по нему видно, если это повторится.

Скрипт для ручной проверки — `tests/manual_doc_smoke.py` (правки, снимки,
откат, без экспорта), полный прогон — `python -m r7 run --suite suites/docs.toml`.
