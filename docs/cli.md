# Командная строка: `python -m r7`

Прогон без окна — для CI, Планировщика заданий и коллег, которым нужен
ответ «можно ли выпускать», а не интерфейс. Тот же воркер, что у вкладки
«Производительность» (`_spreadsheet_worker`), те же отчёты в `Reports/`,
плюс набор тестов в TOML, бюджеты, сравнение с эталоном, JUnit XML и
страница «Релиз готов / Не готов». Код — `r7/cli.py`, `r7/suites.py`,
`r7/gate.py`; шаблон страницы — `templates/html/gate.html`.

Р7-Офис должен быть закрыт, клавиатуру и мышь во время прогона не трогать:
инструмент сам запускает редактор и шлёт ему клавиши. Запускать из сессии
пользователя (не службой), как и ночной прогон.

## Команды

```bat
.venv\Scripts\python.exe -m r7 check
.venv\Scripts\python.exe -m r7 suites
.venv\Scripts\python.exe -m r7 run --suite suites\smoke.toml --gate --junit Reports\junit.xml
.venv\Scripts\python.exe -m r7 run --suite suites\release.toml --baseline Reports\baseline\performance_full_20261007_120000.json --gate --junit Reports\junit.xml --out D:\perf
.venv\Scripts\python.exe -m r7 run --suite suites\smoke.toml --baseline Reports\baseline\performance_full_20261007_120000.json --gate --trace-regressions
.venv\Scripts\python.exe -m r7 trace --op "Вставка большого массива (Ctrl+V)"
.venv\Scripts\python.exe -m r7 bisect --good 2026.3.2 --bad 2026.3.5 --op "Вставка большого массива (Ctrl+V)"
.venv\Scripts\python.exe -m r7 corpus --formats pdf,xlsx
.venv\Scripts\python.exe -m r7 corpus-compare Reports\corpus_20261007_120000.json Reports\corpus_20261009_120000.json
```

| Команда | Что делает |
|---|---|
| `check` | Проверки стенда из мастера первого запуска (`r7/firstrun.py`) без окна: сборка, права, Р7 найден и закрыт, порт CDP, фикстура, диск, масштаб, пакеты. Код 1, если есть ✗. |
| `suites [--dir папка]` | Список наборов `suites/*.toml` с проверкой имён и повторов; битый набор помечен ✗ и даёт код 3. |
| `run --suite файл [--out папка] [--baseline json] [--junit файл] [--gate]` | Прогон набора, отчёты как у вкладки (`performance_full_<ts>.json`, HTML, Excel), таблица итогов в консоль, при `--junit` — JUnit XML, при `--gate` — `gate_<ts>.html` рядом с отчётом. |
| `run ... --trace-regressions` | То же, а после прогона — трасса и профиль операций с регрессией или «вероятной регрессией» к эталону (см. ниже). Без `--baseline` регрессий нет, и трасса не снимается. |
| `bisect --good сборка --bad сборка --op имя` | Первая сборка, на которой операция медленнее базы: двоичный поиск по дистрибутивам с установкой каждой пробы (см. «Бисект по сборкам»). |
| `corpus [--dir папка] [--steps open,recalc,export] [--formats pdf,xlsx] [--hide-names]` | Корпус реальных файлов: открытие, пересчёт и экспорт каждого файла из `Corpus/`, матрица «файл × шаг» в `corpus_<ts>.json` и `.html`. Код 1 — у части файлов ошибка (`docs/corpus.md`). |
| `corpus-compare A.json B.json [...]` | Матрица «файл × версия»: первый отчёт — база, вердикт на каждую ячейку. Код 1 — есть РЕГРЕССИЯ. |
| `trace --op имя [--editor редактор] [--report json] [--out папка]` | Трасса и профиль одной операции на установленном Р7: инструмент сам открывает фикстуру нужного редактора и закрывает Р7. Редактор (`spreadsheet`, `document`, `presentation`) находится по имени операции, `--editor` задаёт его явно. С `--report` файлы ложатся рядом с этим отчётом и дописываются в его `diagnostics`, без него — в папку отчётов и в `diagnostics_<ts>.json`. |

Имена тестов — встроенные и тесты плагинов из `plugins/*.py`
(`docs/plugins.md`): их принимают `--op`, наборы и `suites`. Общий ключ
`--no-plugins` перед командой (`python -m r7 --no-plugins run …`) плагины
не загружает — так прогон идёт только на коде поставки.

`--out` переопределяет папку отчётов (`Reports/` или `reports_folder` из
`r7_settings.json`). `--baseline` — любой `performance_full_*.json`,
например из `Reports/baseline/` или прошлого ночного прогона.

Журнал прогона идёт в консоль с меткой времени и в
`Reports/logs/r7-testovarka.log` (`r7/logfile.py`). Ctrl+C останавливает
после текущей операции, Р7 закрывается штатно, отчёт по сделанному
сохраняется, код выхода — 2.

## Трасса при регрессии

Регрессия видна в цифрах, но не видно, куда ушло время. `--trace-regressions`
(или `"trace_on_regression": true` в `r7_settings.json`) после прогона
открывает Р7 ещё раз и повторяет каждую операцию с регрессией один раз — с
трассой движка и профилем V8. Это отдельный повтор вне замера: в медиану он
не входит. Трасса сама нагружает рендерер, поэтому время этого повтора с
медианой не сравнивают.

Рядом с отчётом появляются `<ts>_<операция>.trace.json` и
`<ts>_<операция>.cpuprofile`. Открыть их можно в ui.perfetto.dev или в
DevTools → Performance → «Загрузить профиль». В `performance_full_<ts>.json`
добавляется ключ `diagnostics`: имена файлов, разбивка по фазам (скрипты,
стили и раскладка, отрисовка, сборка мусора) и 15 самых тяжёлых функций. На
странице готовности у такой операции — ссылки на файлы и строка вида
«скрипты 812 мс; стили и раскладка 40 мс; тяжелее всего asc_Paste (61 %)».
Пакет улик кладёт эти файлы в архив.

Трасса не меняет код выхода: вердикт уже вынесен. Не открылся Р7 или нет
CDP — в журнале предупреждение, отчёт и страница остаются как были.
«Повторное открытие файла» трассой не снимается: это не операция над
открытым документом. Как это устроено — `docs/cdp-operations.md`, раздел
«Трасса при регрессии».

Наборы документа и презентации трассируются так же: вторая сессия Р7
открывает фикстуру своего редактора и повторяет его операции
(`DocumentOps`, `PresentationOps`). Пример:

```bat
.venv\Scripts\python.exe -m r7 trace --op "Смена стиля всего документа"
.venv\Scripts\python.exe -m r7 trace --op "Смена темы" --editor presentation
```

`trace --op` делает то же по требованию, без прогона. Коды выхода: 0 —
трасса снята, 2 — не снята, 3 — нет такой операции (у редактора из
`--editor`), Р7 запущен, нет фикстуры таблиц или отчёта из `--report`.

## Бисект по сборкам

Ночной прогон показал, что Ctrl+V на 2026.3.5 медленнее, чем на 2026.3.2, а
между ними в `Distributives/` лежат ещё десять сборок. Какая из них
виновата? `bisect` отвечает на это сам: ставит сборки по очереди и делит
отрезок пополам, как `git bisect`.

```bat
.venv\Scripts\python.exe -m r7 bisect --good 2026.3.2 --bad 2026.3.5 --op "Вставка большого массива (Ctrl+V)"
.venv\Scripts\python.exe -m r7 bisect --good R7-Office-2026.3.2.100.exe --bad R7-Office-2026.3.3.17.exe --op "Функция ВПР (50K строк)" --runs 9 --max-runs 27
```

| Параметр | Что значит |
|---|---|
| `--good`, `--bad` | База и плохая сборка: имя файла, путь или номер версии. Номер может быть началом полного: `2026.3.2` найдёт `2026.3.2.100`, если такой файл один. |
| `--op` | Одна операция, имя точно как в `TEST_DEFINITIONS`. «Повторное открытие файла» бисект не меряет. |
| `--runs` | Повторов за один заход на сборку, по умолчанию 7, не меньше 5. |
| `--max-runs` | Потолок повторов сборки, если она «не определено», по умолчанию 21. |
| `--dist` | Папка дистрибутивов вместо `Distributives/`. |
| `--no-restore` | Не возвращать исходную версию в конце. |
| `--out` | Папка отчётов вместо `Reports/`. |

Нужны права администратора: бисект ставит и удаляет Р7 тем же путём, что
Batch (удаление по проверенной команде msiexec, тихие ключи по типу
установщика). Р7 должен быть закрыт, фикстура 50К — на месте.

### Как ищет

1. Сборки из папки сортируются по номеру версии числами (2026.10 идёт после
   2026.9). Файлы без номера в имени в бисект не входят, о них пишется в
   журнал.
2. Сначала меряются база и плохая. `compare_runs` с порогом теста (из
   профиля шума стенда, без профиля 10 %, см. `docs/statistics.md`) должен
   сказать «РЕГРЕССИЯ». Не сказал — искать нечего, бисект останавливается с
   объяснением. Если разница пока «не определено», крайние получают ещё по
   заходу, пока не наберут `--max-runs`.
3. Дальше каждая проба — середина отрезка. Её повторы сравниваются с обеими
   крайними:
   - **как база** — проба эквивалентна базе или значимо быстрее плохой;
   - **как регрессия** — значимо медленнее базы или эквивалентна плохой;
   - **не определено** — ни то, ни другое. Сборка получает ещё заход (по
     `--runs` повторов), пока не наберёт `--max-runs`.
4. Сборка, которая так и осталась «не определено» или не измерилась
   (установка упала, Р7 не открылся, годных повторов нет), пропускается, как
   `git bisect skip`. Следующая проба — ближайшая к середине.
5. Итог — первая сборка «как регрессия» сразу после последней «как база».
   Если между ними остались пропущенные, ответ — отрезок: «одна из N сборок».

Проб нужно ⌈log₂(N − 1)⌉ для N сборок в отрезке: на 12 сборках это 4 пробы
плюс 2 крайние. Каждая проба — удаление, установка, открытие фикстуры и
7 повторов, примерно 5–10 минут.

Проба может быть медленнее базы и при этом быстрее плохой. Это значит, что
сдвигов несколько. Такая сборка считается плохой (первый сдвиг за порог уже
случился), в отчёте у неё пометка «промежуточная». Бисект находит первый
сдвиг, который сам по себе больше порога. Если регрессия набиралась мелкими
шагами по 1 %, ответ будет той сборкой, где сумма перешла порог.

### Исходная версия

По умолчанию в конце ставится та версия, что стояла до бисекта, — и после
ошибки, и после Ctrl+C. Её дистрибутив должен лежать в той же папке: если
его нет, бисект не начинается и просит положить файл или добавить
`--no-restore`. Если сборка уже стоит (база совпадает с исходной, добор
повторов), второй раз она не ставится. Не удалось вернуть исходную — в
журнале и на странице красная строка с именем файла, код выхода 2.

### Отчёт

В папке отчётов появляются `bisect_<ts>.json` (итог, все пробы с повторами
и сравнениями, журнал заходов) и `bisect_<ts>.html`: вердикт, сдвиг плохой
к базе с интервалом, таблица всех сборок отрезка (роль, n, медиана, Δ к базе
и к плохой, класс, пометка) и строка про исходную версию. В консоль идёт та
же таблица проб.

Коды выхода: 0 — первая плохая сборка найдена; 1 — ответа нет (крайние не
различаются, плохая быстрее базы, или пропуски оставили отрезок); 2 —
бисект не дошёл до конца (крайнюю сборку не измерить, Ctrl+C) или исходная
версия не вернулась; 3 — условия не выполнены (нет прав, Р7 запущен, нет
фикстуры, сборка не найдена или неоднозначна, нет дистрибутива исходной
версии, идёт другой прогон).

Код: алгоритм — `r7/bisect.py` (без Tk и установок, проверяется на
синтетике), установка и замер — `r7/bisect_runner.py` (`BisectMixin`),
страница — `r7_reports.bisect_model` и `templates/html/bisect.html`.
Пока идёт бисект, `RunState` держит вид `bisect`: ни прогон, ни установка,
ни сценарий не запустятся.

## Коды выхода

| Код | Значение |
|---|---|
| 0 | Все операции набора в норме: бюджеты не превышены, регрессий к эталону нет. |
| 1 | Хотя бы одна операция выше бюджета, с регрессией, с ошибкой или не измерена (`run`); есть ✗ (`check`). |
| 2 | Прогон не удался: отчёта нет, воркер упал, прерван Ctrl+C. |
| 3 | Условия не выполнены: Р7 запущен или не найден, нет фикстуры 50К, набор или эталон не читаются. |

## Формат набора

```toml
[suite]
name = "smoke"
description = "Открытие и три ключевые операции, ~5 минут"
editor = "spreadsheet"                # необязательно: "spreadsheet" (по умолчанию) | "document" | "presentation"

[tests]                               # имя — точно как в TEST_DEFINITIONS
"Повторное открытие файла" = 3        # повторов, 1..20 (RUNS_MIN..RUNS_MAX)
"Выделение всех ячеек (Ctrl+A)" = 5

[budgets]                             # необязательно: потолок медианы, секунд
"Повторное открытие файла" = 12.0

[compare]                             # необязательно
min_effect_pct = 10                   # порог практической значимости compare_runs
```

- Имя теста с опечаткой — ошибка со списком допустимых имён. Повторы вне
  1..20 обрезаются, как в поле «×N»; не целое — ошибка.
- Бюджет можно задать только тесту из `[tests]`; значение — число больше нуля.
- Неизвестный раздел (`[test]` вместо `[tests]`) — ошибка, а не молчаливый пропуск.
- `editor = "document"` — набор текстового редактора: имена тестов сверяются
  с `r7_doc_ops.DOCUMENT_TEST_DEFINITIONS`, прогон идёт `_document_worker`,
  фикстура `TestFiles/r7-test-doc-100p.docx` создаётся сама, эталон должен
  быть снят на том же редакторе (поле `editor` отчёта; без поля — таблицы),
  трасса регрессий снимается на операциях документа. Подробности —
  `docs/document-ops.md`.
- `editor = "presentation"` — то же для презентаций: имена из
  `r7_pptx_ops.PRESENTATION_TEST_DEFINITIONS`, прогон `_presentation_worker`,
  фикстура `TestFiles/r7-test-slides-50.pptx` создаётся сама. Подробности —
  `docs/presentation-ops.md`.
- `suite_to_selection(suite, TEST_DEFINITIONS)` даёт структуру
  `selected_tests.json` — интерфейс сможет загрузить набор как выбор тестов.

Поставляемые наборы: `smoke.toml` (открытие ×3, Ctrl+A, Ctrl+V, ВПР ×5),
`release.toml` (все 17 тестов с повторами по умолчанию и двумя бюджетами
с запасом), `export.toml` (четыре экспорта ×3), `docs.toml` (документ
.docx: открытие ×3, три правки ×5, экспорт PDF и DOCX ×3), `slides.toml`
(презентация .pptx: открытие ×3, четыре правки ×5, экспорт PDF и PPTX ×3). ODS на фикстуре 50К роняет
x2t (DE-8304) — в `release` и `export` он даст «ошибка» и «Не готов».

## Вердикт и страница готовности

`r7/gate.py` считает по каждому тесту набора:

| Вердикт | Когда |
|---|---|
| в норме | медиана не выше бюджета, регрессии к эталону нет |
| выше бюджета | медиана больше `[budgets]` |
| регрессия | `compare_runs` (Манн-Уитни, p < 0,05, сдвиг больше `min_effect_pct`) по действительным повторам — тем же, что вошли в медиану |
| ошибка | ни одного действительного повтора (`error` в записи) |
| не измерено | операция из набора в отчёт не попала (прогон прерван) |

«Релиз готов» — все в норме; любая причина против — «Не готов». Меньше
пяти повторов на любой стороне — вердикта сравнения нет, показана только
Δ %. Эталон другой схемы замера или той же версии Р7 — предупреждение на
странице. Открытие в наборе называется «Повторное открытие файла», а в
отчёте — «Открытие файла» (`gate.result_name`).

Страница `gate_<ts>.html`: один крупный блок вердикта с причинами, таблица
(медиана ± MAD, n, бюджет, эталон, Δ, вердикт, причина), «Как считалось».
Оформление — `base.html`: токены цвета, светлая и тёмная темы, печать в PDF.

## JUnit для CI

`--junit` пишет один `<testsuite>` с `<testcase>` на каждый из 17 тестов:
`failure` — выше бюджета или регрессия, `error` — ошибка или не измерено,
`skipped` — тест в набор не входит. Любой CI (GitHub Actions, GitLab,
Jenkins) покажет его как результаты тестов. Пример шага на self-hosted
раннере с меткой `r7-installed`:

```yaml
- run: .venv\Scripts\python.exe -m r7 run --suite suites\smoke.toml --gate --junit Reports\junit.xml
- uses: actions/upload-artifact@v4
  if: always()
  with: { name: perf, path: Reports/ }
```

Код выхода 1 завершит шаг с ошибкой, как и ожидает CI; 2 и 3 — тоже, но
по причинам стенда, а не Р7 — смотрите журнал.

## Как устроен прогон без окна

`cli.make_headless_app` собирает `R7Testovarka` через `__new__` и
`_init_state()` (состояние прогона и папки — всё, что в `__init__` не Tk),
подменяет `add_test_log`, `_ui_call`, `_set_perf_progress` и
`_show_post_test_dialog` заглушками и читает версию Р7 из реестра
(`_read_current_version_from_registry`, безопасна вне главного потока).
`r7_Testovarka` импортируется лениво только в `r7/cli.py`: при
`python -m r7` он не `__main__`, второй копии класса нет. Воркер идёт в
фоновом потоке, главный ждёт его короткими `join`, чтобы ловить Ctrl+C и
ставить `stop_event`.
