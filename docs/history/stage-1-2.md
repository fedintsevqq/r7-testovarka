# История: нагрузочный стенд, этапы 1–2 (август 2026)

> Перенесено из `CLAUDE.md` 30.09.2026 без изменений текста. Раздел описывает, как и почему
> устроен код, включая историю отладки. Часть фактов здесь могла устареть — при расхождении

### Нагрузочный стенд: этап 1 (медиана/MAD, нормировка CPU, окружение)

По итогам отчёта «Нагрузочный контур R7» (25.08.2026): бимодальность
`settle_ms` (до 27× разброса между прогонами одного файла — см. `api_ms`
выше) требовала не только вторую метрику, но и починки самой статистики по
прогонам и детекторов простоя. `measure_schema` в JSON различает старую и
новую версию замера.

#### Медиана + MAD вместо среднего (`run_test_with_runs`)

Одно среднее по `DEFAULT_TEST_RUNS` (теперь 7, было 3) прогонам — способ
увидеть регрессию там, где её нет: один выброс сдвигает среднее
непропорционально (проверено эмпирически на живом Р7: 7 повторов Ctrl+C дали
разброс отдельных прогонов 1.59–2.43 с, при этом медиана — 1.6067 с и 1.6005 с
в двух независимых сессиях, разница между сессиями 0.39%).

* Первый прогон отбрасывается как прогрев (JIT/кэши/CDP-соединение) — но
  только если после отбрасывания останется хоть один прогон
  (`MIN_RUNS_FOR_STATS = 2`).
* `R7Testovarka._mad(values, center=None)` — Median Absolute Deviation,
  устойчивая мера разброса рядом с медианой. В `statistics` готовой функции
  для неё нет (есть `stdev`, но не MAD). Не масштабируется константой 1.4826
  (перевод в оценку сигмы для нормального распределения) — скорость операций
  Р7 ничем не гарантированно нормальна, MAD интересен как «типичное
  отклонение от медианы» в секундах.
* `results[...]["time"]` теперь = медиана (headline-значение отчётов и
  сравнения версий). Ключи `avg`/`min`/`max` оставлены БЕЗ ИЗМЕНЕНИЙ —
  обратная совместимость с уже сохранёнными `performance_full_*.json` и их
  читателями. Новые ключи: `median`, `mad`, `n_runs` (сколько прогонов вошло
  в статистику после отбрасывания), `first_run_discarded`.
* Batch-режим (`measure()`) статистику не считает — там один прогон на
  операцию по конструкции; медиана/MAD относятся только к вкладке
  «Производительность».

#### Нормировка CPU на число ядер (`_wait_operation_done`, `_wait_until_r7_ready`)

**Отменено аудитом 29.09.2026 (`measure_schema` 3)** — см. «Аудит точности
замеров». Ниже — история, почему нормировку вводили.

До 25.08.2026 (`measure_schema` 1) пороги `OP_IDLE_CPU_PCT`/`READY_IDLE_CPU_PCT`
сравнивались с СЫРОЙ суммой `cpu_percent()` по процессам Р7 — момент
«простаивает» зависел от числа ядер стенда: то же реальное состояние (один
поток на 100%) на 4-ядерной машине даёт сумму ~100, на 16-ядерной — тоже
~100, но это разные доли мощности машины. `R7Testovarka._cpu_count()`
(закэшированный `psutil.cpu_count()`, `or 1` — API документированно может
вернуть `None`) переводит пороги в шкалу Task Manager (0–100% = вся машина):
`OP_IDLE_CPU_PCT = 4.0`, `READY_IDLE_CPU_PCT = 3.0` — первая калибровка,
подтверждена вживую (busy/idle детектор не залипает ни в `timeout`, ни во
всегда-`ok`), но НЕ проверена на парке разного железа за пределами одной
машины. `_sample_r7_resources` нормировала CPU так и раньше — эта правка
приводит к тому же формату детекторы простоя, у которых была рассинхронизация.

#### Окружение прогона и версия схемы (`_build_system_info`, `MEASURE_SCHEMA_VERSION`)

Блок `"system"` в JSON (`os`, `ram_total_gb`, `cpu_model`) уже существовал —
новое здесь: `cpu_cores_logical` (нужен, чтобы восстановить смысл
нормированного CPU% при чтении старого файла на другой машине) и
`measure_schema` на верхнем уровне `performance_full_*.json`. Файлы без
этого поля — читать как версию 1 (сырые пороги CPU, `time` = среднее);
`measure_schema: 2` — нормированные пороги, `time` = медиана. Общий код
вынесен в `_build_system_info()` — раньше дублировался дословно в
одиночном и Batch-воркерах.

#### Детерминированный выбор CDP-цели по имени файла (`R7WebDriverConnector.filename_hint`)

ПРОВЕРЕНО НА ЖИВОМ Р7 (25.08.2026, два документа в одном экземпляре): у ВСЕХ
целей-редакторов в ответе `/json` поле `title` — одна и та же строка
"R7-OFFICE Documents", бесполезная для различения документов. Настоящее имя
файла лежит в query-параметре `title=` самого URL цели
(`...&title=test_50k.xlsx&...`) — извлекается `R7WebDriverConnector._target_filename()`
через `urllib.parse` (не подстрокой: имя может быть URL-экранировано).

`R7WebDriverConnector(port, log_cb, filename_hint=...)` — если задан,
`_pick_target()` ищет среди целей с `doctype=` в URL именно ту, чей
`title=`-параметр совпадает с `filename_hint`. Не совпало ни с одной (редактор
ещё не проставил параметр, документ пересохранён под другим именем) —
не `None` (это заставило бы `connect()` решить, что редактор не загрузился, и
поллить впустую до таймаута), а первая подходящая цель с явным
предупреждением в лог. `filename_hint=None` (по умолчанию, все сегодняшние
вызывающие места) — прежнее поведение без фильтра, для однодокументного
сценария не отличимо. Готовит почву для Stage 3 (H4, многодокументный режим) —
сам многодокументный запуск ещё не реализован, только выбор цели.

`_prepare_webdriver_launch(log_cb, filename_hint=...)` прокидывает подсказку
в конструктор коннектора; все три места запуска Р7 (`_spreadsheet_worker`,
`_batch_run_single_version`, `_worker_run_test`) передают `test_file.name`.
При подключении с подсказкой в лог пишется `🔍 CDP-цель: {имя} (по файлу
{подсказка})` — подтверждено вживую.

### Нагрузочный стенд: этап 2 (наблюдаемость и регрессии)

#### Фоновый семплер ресурсов и детектор утечек (H3)

`ResourceSampler` (`threading.Thread`) снимает точку раз в `interval` секунд:
RSS процессов Р7 (`psutil`, всегда) и `JSHeapUsedSize`/`Documents` через
`R7WebDriverConnector.performance_metrics()` (только если передан
подключённый коннектор). Ошибка одного источника на одном замере не роняет
поток — соответствующее поле остаётся `None`, семплер продолжает работать
дальше. `snapshot()` — потокобезопасная копия накопленного ряда.

`performance_metrics()` — новый метод коннектора поверх штатного домена CDP
`Performance` (`enable` один раз лениво + `getMetrics`). Эти цифры снимает
сам движок CEF, а не наш JS — не искажаются им, в отличие от `evaluate()`.
Только для бэкенда `"cdp"`: `Performance.getMetrics` — команда протокола, а
не JS API, `driver.execute_script()` (бэкенд `"selenium"`) её вызвать не
может в принципе. Транспорт (`send`/`recv`/обработка обрыва) вынесен в общий
`_cdp_send(method, params, timeout)` — `_eval_cdp` (Runtime.evaluate)
отрефакторен на него же, дублирования не осталось.

**ПРОВЕРЕНО НА ЖИВОМ Р7** (25.08.2026): `JSHeapUsedSize` реален и вменяем
(~43–45 МБ на тестовом документе). Но CDP-метрика `Documents` — это
**внутренний счётчик DOM-документов CEF-рендерера** (фреймы, служебные
контексты), а НЕ «сколько файлов открыл пользователь»: на живом прогоне с
ОДНИМ открытым файлом и без единого действия пользователя она сама уехала
228 → 232 за 4 секунды простоя. `detect_leak()` учитывает это: «стабильность»
числа документов — допуск `DOC_COUNT_STABLE_TOLERANCE_FRAC` (10% от
начального значения, первая калибровка по одному короткому живому
наблюдению), а не точное равенство — иначе почти каждый реальный прогон
ложно читался бы как «пользователь открыл второй документ».

`detect_leak(samples, key="heap_mb", threshold_mb_per_hour=5.0, min_samples=30)`
— наклон линейной регрессии (`_linear_slope`, метод наименьших квадратов
без numpy — ряд соизмерим с частотой опроса раз в секунду на несколько
часов, не миллионы точек) выше порога ПРИ стабильном числе документов =
утечка. `threshold_mb_per_hour=5.0` — тоже первая калибровка, не
подтверждённая многочасовым soak-прогоном (Stage 3). `leak: None` (не
`False`) означает «не удалось оценить» (мало точек/вырожденная выборка) —
вызывающий код обязан различать это от «утечки нет».

**Потокобезопасность (найдено code-review, до первого реального
использования).** `ResourceSampler` — фоновый поток, который поллит
`performance_metrics()` тем же `R7WebDriverConnector`, которым продолжает
пользоваться основной поток теста (CDP-операции, опрос при закрытии Р7 раз
в секунду). Один `websocket`/`_ws_msg_id` на двоих без блокировки — гонка:
один поток может забрать `recv()`-ответ, адресованный другому. Добавлен
`R7WebDriverConnector._cdp_lock` (`threading.Lock`), которым обёрнут весь
`_cdp_send()`. Регрессионный тест (`test_cdp_send_is_locked_against_concurrent_callers`)
детерминированно (не по таймингу) ловит нарушение через фейковый websocket,
падающий при параллельном входе в критическую секцию — проверено вручную:
без блокировки тест валится 3 из 3 запусков, с ней — ни разу.

Побочный эффект блокировки, **найден живым прогоном** (25.08.2026): пока
основная CDP-операция держит лок (например, `Копирование выделения` заняло
~14 с реального времени), опрос семплера тоже блокируется на это время —
плотность замеров падает ниже номинальных «раз в секунду». На живом прогоне
(76 с, 3 операции × 3 повтора) собралось 18 точек `heap_mb` вместо ожидаемых
~59 — `detect_leak` корректно отдал `leak: None` ("недостаточно замеров"),
как и задуман: `min_samples=30` — не жёсткая гарантия частоты опроса, а
защита от вердикта на шумных/редких данных. Для soak-теста (Stage 3, часы,
не секунды) это не проблема; для короткого одиночного прогона — ожидаемое
поведение, не баг.

**Интеграция**: `ResourceSampler` создаётся в `_spreadsheet_worker` рядом с
`_upd_stop` (до внешнего `try`, тем же паттерном — гарантирует, что имя
определено к моменту `finally`, даже если код упадёт на первой строке),
`.start()` — у начала цикла операций (не раньше: до этого RAM/CPU ещё
формируются открытием файла), `.stop()`+вердикт — сразу после цикla операций,
до сохранения отчётов (снимок должен покрывать сам прогон). `finally`
дополнительно зовёт `.stop()` (идемпотентно) на случай исключения. Вердикт
пишется в `summary.leak_detection` JSON-отчёта. Batch-режим не подключён —
там один замер на операцию, соак-подобный анализ не имеет смысла в этой
архитектуре (Stage 3, если понадобится).

#### Сравнение версий: Манна-Уитни без scipy (M5)

`compare_runs(base_times, new_times, min_effect_pct=10.0, alpha=0.05, min_runs=5)`
— вердикт `РЕГРЕССИЯ`/`УСКОРЕНИЕ`/`без изменений`/`недостаточно прогонов`.
Регрессия/ускорение объявляются только при ОБОИХ условиях: статистическая
значимость (p < alpha) И практическая (`|effect_pct| > min_effect_pct`) —
на достаточно большом N даже 2%-й сдвиг станет «значимым», но веса для
решения не имеет. Опирается на медиану (`statistics.median`), не на
среднее — согласовано с этапом 1 (H2).

**Осознанное решение — без scipy.** Документация scipy (проверено через
context7 при разработке) подтверждает: с версии 1.7 `mannwhitneyu` по
умолчанию считает ТОЧНЫЙ p-value для маленьких выборок без связей — честнее
приближения. Но scipy тянет numpy, десятки МБ веса для инструмента,
распространяемого как компактный portable-архив, а requirements.txt сейчас
— только лёгкие пакеты. `_mann_whitney_u(x, y)` — собственная реализация:
нормальное приближение с поправкой на связи (ties) и непрерывность,
`_normal_cdf` через `math.erf` (стандартная библиотека, точно, не
приближённо). При N=5..10 (реалистичный диапазон — см. `DEFAULT_TEST_RUNS`)
разница с точным расчётом для вывода регрессия/без-изменений пренебрежимо
мала.

**Как проверялась корректность без scipy под рукой**: `tests/test_compare_runs.py`
содержит независимый брутфорс-оракул (`_exact_mann_whitney_p`) — полный
перебор всех перестановок разметки объединённой выборки (единственный
способ получить точный p-value без scipy), и `_mann_whitney_u` сверяется
против него на 6 представительных случаях (полное разделение, частичное
перекрытие, полное совпадение, связи, равные/неравные N) — совпадение
вывода о значимости на `alpha=0.05` для каждого, численная близость p в
пределах 0.15. Не «выглядит правдоподобно» — фактически проверено.

**Интеграция (найдено code-review: реализовано, но нигде не вызывалось —
заявленный критерий готовности этапа 2, "прогон двух версий даёт
автоматический вердикт", не выполнялся ни одним реальным путём).**
`_generate_comparison_html` — третья колонка «Вердикт (M5)» на каждую
не-базовую версию. Данные — `results[...]["runs"]` (сырые повторы), их
пишет только одиночный прогон вкладки «Производительность»
(`run_test_with_runs`); Batch-режим делает один замер на операцию и `"runs"`
не сохраняет вовсе — для таких файлов и при `n < MIN_RUNS_FOR_COMPARISON`
(5) колонка показывает прочерк с пояснением в `title`, вердикт не
выносится. Колонка базовой версии — тоже прочерк (сравнивать версию саму с
собой и печатать «без изменений» было бы вводящим в заблуждение
статистическим утверждением о нулевой разнице).

#### Регрессия, пойманная только живым прогоном (25.08.2026)

`run_test_with_runs` — вложенная функция внутри `_spreadsheet_worker`, её
нельзя вызвать напрямую в юнit-тесте (нужен живой Р7/Tk-контекст — см.
собственный docstring `tests/test_stage1_metrics.py`). Более ранняя правка
`/simplify` (этап 1) убрала параметр `center` у `_mad()`, но единственный
реальный вызов — `self._mad(stats_times, median_t)` — остался с двумя
аргументами. 179+ юнит-тестов этого не поймали: тесты самой `_mad()`
вызывают её С ЕЁ ЖЕ, а не с фактической (используемой в коде), сигнатурой —
рассинхронизация вызывающего кода и определения структурно невидима для
такой проверки.

Всплыло на живом прогоне через настоящий `_spreadsheet_worker` (не через
`tests/manual_cdp_smoke.py`, который вызывает `_cdp_*`-методы напрямую, минуя
`run_test_with_runs` целиком): `TypeError` после трёх успешных повторов
Ctrl+A, необработанное исключение вне try/finally, закрывающего Р7 —
процесс остался висеть (пришлось убивать вручную, 8+ минут). Это
дополнительно вскрыло архитектурный факт: необработанное исключение в
середине `_spreadsheet_worker` не закрывает Р7 (шаг «Закрытие» — линейный
код после цикла операций, не в `finally`) — отдельный, не устранённый в
этом PR риск, за пределами того, что вызвало эту конкретную регрессию.

Исправлено (`self._mad(stats_times)`) и подтверждено повторным живым
прогоном — полный цикл (3 операции × 3 повтора, включая семплер и
блокировку CDP) прошёл без исключений, Р7 закрылся штатно. Добавлен
регрессионный тест (`test_run_test_with_runs_calls_mad_with_correct_arity`)
— интроспекцией (`inspect.getsource` + сверка арности с реальной сигнатурой
`_mad`) проверяет исходный код вызова напрямую, а не переreализует его
отдельно (что унаследовало бы ту же рассинхронизацию). Подтверждено:
падает 3 из 3 запусков на двухаргументном вызове, зелёный на исправленном.

**Вывод для дальнейшей работы**: любое изменение сигнатуры метода,
вызываемого из вложенной функции внутри `_spreadsheet_worker` (или
`_batch_run_single_version`), требует живого прогона перед тем, как
считаться проверенным — юнит-тесты по конструкции не видят эти call sites.

#### Генератор фикстур с профилями нагрузки (M2)

`R7Testovarka._generate_fixture(path, rows=100_000, profile="flat", seed=42, cols=6)`,
`FIXTURE_PROFILES = ("flat", "formula", "styled", "mixed")`. Один и тот же
объём данных по-разному нагружает Р7 в зависимости от того, ИЗ ЧЕГО он
состоит (см. отчёт по нагрузочному тестированию, раздел про «жирный текст»):

* `flat` — числа + разнородный текст, БЕЗ формул и уникальных стилей.
  Парсер значений и аллокация ячеек.
* `formula` — колонка "Chain" каждой строки ссылается на "Chain" предыдущей
  строки данных — граф зависимостей длиной `rows`, движок пересчёта не
  может распараллелить. **Пойманный тестами баг**: ссылка `C{i-1}` (где
  `i` — счётчик данных с 1, БЕЗ учёта строки заголовка) для `i=2` указывала
  на `C1` — строку заголовка, а не на предыдущие данные; для бо́льших `i`
  тихо ссылалась на данные через одну строку назад, ломая топологию цепочки
  без единой видимой ошибки формулы. Исправлено на `C{i}` (сдвиг строки
  листа на 1 из-за заголовка компенсирован).
* `styled` — уникальный шрифт/заливка почти на каждой строке (через
  `WriteOnlyCell` — `write_only=True` не даёт произвольный доступ к
  ячейкам, стили ставятся ДО `append()`). Раздувает таблицу стилей
  (styles.xml), а не таблицу данных — то, что «жирный текст» не трогает.
* `mixed` — числа + формулы + стили через строку, ближе всего к реальному
  документу.

Значения намеренно РАЗНЫЕ (`random.Random(seed)`, не константа) — однородный
текст даёт быстрый путь дедупликации в `sharedStrings` и завышает результат
(та же ловушка, что у «жирного текста»). `seed` — воспроизводимость: разные
версии Р7 должны тестироваться на буквально одном и том же файле.

Живая проверка формул (реально вычисляются в Р7, не просто валидный текст
формулы) технически невозможна тем же способом, что и раньше в этом
проекте: сетка Р7 — `<canvas>`, значения ячеек не читаются через DOM.
Корректность подтверждена структурно (юнит-тест на то, что каждая формула
ссылается на строку листа `i`, а не `i-1`) и математикой индексов, не
визуальным вычислением в живом Р7.

#### Страница трендов (M5)

Кнопка «📈 Тренды» на вкладке «Производительность» → `show_trends()` →
`_load_trends_runs()` (чтение всех `performance_full_*.json` из
`reports_folder`, хронологически по mtime, битые файлы пропускаются молча)
→ `_generate_trends_html(runs)` (чистая функция от уже загруженных данных —
разделено специально для тестируемости без диска). Один график Chart.js на
операцию (та, что встретилась минимум в двух прогонах — из одной точки
тренда не построить), точки раскрашены по версии Р7, полоса MAD вокруг
линии медианы там, где MAD посчитан (`measure_schema=2`) — двумя служебными
датасетами (`fill: '-1'`), не через отдельный plugin (лишняя CDN-зависимость
ради одной фичи). Тот же баннер-предупреждение про смешанные
`measure_schema`, что и в `_generate_comparison_html`.

Проверено на реальных 14 накопленных `performance_full_*.json` этого
репозитория — README: время открытия файла на графике падает с ~30 с до
~7.5 с по ходу истории коммитов, что отражает реальный прогресс CDP-миграции
(этап 0) внутри проекта.

#### CI (два уровня)

`.github/workflows/tests.yml` — юнит-тесты на `windows-latest`, секунды,
без побочных эффектов, PROVEN: гоняется на каждый push/PR. Включает
py_compile, pyflakes (по `r7_Testovarka.py`, `r7_webdriver_connector.py`,
`tests/`), проверку `WEBDRIVER_OK` и сам `pytest`.

`.github/workflows/perf.yml` — **НЕ ПРОВЕРЕН ЖИВЫМ ЗАПУСКОМ**. Требует
self-hosted раннера с меткой `r7-installed` (GitHub-hosted раннеры не дают
поставить на них Р7-Офис — нужен GUI, интерактивная сессия, лицензия).
Такого раннера в проекте пока нет — файл рабочий черновик под будущую
инфраструктуру. Запускает `tests/manual_cdp_smoke.py` вручную/по расписанию
(не на каждый push — живой прогон трогает реальный Р7 на машине раннера).
